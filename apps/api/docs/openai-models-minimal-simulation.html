LinkGen · simulated document run

How one prompt becomes a minimal carousel.

This is a walkthrough and HTML preview for the prompt: “Create a document about OpenAI’s new models Sol, Terra and Luna.”

Simulation boundary: the pipeline was not executed and no live web research was performed. Sol, Terra, and Luna are treated as fictional model names for this example. Their capabilities below are illustrative assumptions, not verified OpenAI product facts.

1. The request enters the system

Visual theme and writing voice are separate inputs.

Simulated build input

{
  "type": "DOCUMENT",
  "prompt": "Create a document about OpenAI's new models Sol, Terra and Luna.",
  "withResearch": true,
  "stylePreset": "educational",
  "theme": "minimal",
  "kind": "INITIAL"
}

What those fields mean

DOCUMENT
Generate a 2–15 slide LinkedIn carousel.
withResearch
Insert the agentic research step for this initial run.
educational
Use structured, practical, plain-language writing.
minimal
Stamp the visual theme authoritatively onto the deck.
INITIAL
Run fresh research; later refines reuse cached findings.

3. Simulated RESEARCH output

In production, these would be live tool calls.

Queries the research agent might choose

  • “OpenAI Sol model announcement”Check whether Sol has a primary announcement and what its stated positioning is.
  • “OpenAI Terra model reasoning capabilities”Look for evidence of reasoning, latency, context, or evaluation claims.
  • “OpenAI Luna multimodal model use cases”Check whether Luna is associated with multimodal or creative workflows.

ResearchResult.findings

Simulation synthesis: Treat Sol, Terra, and Luna as three newly announced models with intentionally different jobs. For this walkthrough, Sol represents fast general-purpose execution, Terra represents deeper multi-step reasoning, and Luna represents multimodal collaboration and creative exploration.

These are bounded assumptions for the simulation. A real research run would only pass claims to GENERATE if the search results supported them. The final writer should not present these labels or capabilities as verified facts outside this hypothetical brief.

4. RunState after each step

The engine shallow-merges each step’s patch.

After RunState slots Durable side effect
RESOLVE_INPUT input Nothing durable beyond the existing run record.
RESEARCH input, research Save researchContext so a future refine can skip web search.
GENERATE input, research, content Nothing persisted yet; content is Zod-validated first.
RENDER_PDF Previous slots + render Upload artifacts/<artifactId>/1/document.pdf and return its pdfKey.
PERSIST_VERSION Final state Write content + render metadata; version becomes READY.

What happens after this preview: RENDER_PDF stores the derived PDF under a version-scoped R2 key, and PERSIST_VERSION stores that key—not a public URL. On a later refine, RESEARCH is skipped, cached findings are seeded during RESOLVE_INPUT, the deck is regenerated, and the new version is rendered to a new PDF key.
